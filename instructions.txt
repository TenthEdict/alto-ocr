Delivery structure for a digitized, transcribed object
=====================================================

One Ref ID delivers as ONE FLAT FOLDER. Every file for the object sits
directly in that folder -- no subfolders -- so that LibSafe holds the images,
the OCR outputs and the manifest as a single item:

    <container>/<Collection Name>/digitize-scans/preservation-files/<RefID>/
        page001.tif          preservation copy; canonical, NOT produced by the OCR tool
        page001.xml          ALTO -- produced by the OCR tool
        page001.txt          plain-text transcript -- produced by the OCR tool
        page002.tif
        page002.xml
        page002.txt
        ...
        <RefID>.mets.xml     manifest describing all of the above

Every page contributes the same set of files, named identically except for the
extension. The METS references all three file types with bare filenames as
hrefs, because the delivered folder is flat.

  <container>       LibSafe container number, e.g. 50
  <Collection Name> e.g. "Anne M. Lutz Papers"
  <RefID>           e.g. MSA00163_df5ebf121773e0f868004a83d0673134

Neither the container number nor the collection name is derivable from the Ref
ID; both come from the workflow (a Goobi project per collection, or a process
property).

Superseded design (do not reintroduce)
-------------------------------------

Until 2026-08-24 this file described two sibling trees --
`preservation-files/preservation/<RefID>/` for TIFFs and
`documentation/ALTOS-Plain Text/<RefID>/` for ALTO and text -- paired by Ref ID
externally by LibNova, with a METS that deliberately did NOT reference the
TIFFs so as not to duplicate them onto the documentation tree.

That model is retired: everything is co-located, and the METS therefore
describes the images too. A manifest that listed only two thirds of the files
beside it would be worse than no manifest, because it looks authoritative.

Working layout inside the pipeline
----------------------------------

The delivered layout is NOT the pipeline's working layout. While an object is
in the workflow, Goobi's own conventions apply:

    <process>/images/<RefID>_master/     TIFFs (flat -- Goobi requires it)
    <process>/ocr/<RefID>_alto/          ALTO
    <process>/ocr/<RefID>_txt/           plain text
    <process>/ocr/alto_ocr/<RefID>/      view onto the two above, plus the
                                         working METS (nested ALTO/ + Text/
                                         hrefs, describing THIS layout)

The delivery package is assembled at upload time: files are flattened into one
folder and a delivery METS with flat hrefs is written for it. The working METS
stays as it is -- it is this tool's own fixity record, and the re-OCR guard
uses its checksums to notice corrections made by editors that leave no
provenance of their own.

Sub-collections: not nesting (settled 2026-08-24)
-------------------------------------------------

"Sub-collections" are SIBLING Ref IDs, not folders inside a Ref ID. A
collection subdivides by suffixing the Ref ID, and each subdivision is a
complete object with its pages flat inside it:

    MSS00021 Gaddis, Bertha Kate diaries/preservation-files/preservation/
        MSS00021_001/MSS00021_001_00001.tif ... (208 pages, flat)
        MSS00021_002/ ... (216 pages, flat)
        ... through MSS00021_018

Checked across all 18 Ref IDs of that collection: zero subdirectories, zero
nested TIFFs, 5,030 pages total. So each sub-collection is simply its own
Goobi process with its own Ref ID, which is already how the pipeline works --
no flattening, no subpath map, no reconstruction at delivery.

The import step's refusal of nested input therefore never fires on real data.
Keep it anyway: it is cheap, and it fails loudly rather than silently
mangling preservation copies if the convention ever changes.

Page size varies enormously by material and no single figure represents it:

    diaries (MSS00021)           1397x2106   2.9 MP    ~7 MB/page
    letter-size reports          4698x3798  17.8 MP   ~50 MB/page
    oversize sheet               12409x4773 59.2 MP  ~177 MB/page

All at 400-500 dpi. Storage and OCR-time estimates must state which material
they assume.
